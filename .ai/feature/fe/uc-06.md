# UC-06 — Frontend

## Cel
- Pokazać użytkownikowi administracyjnemu listę modeli bazowych z rejestru oraz listę gotowych datasetów `.npz`.
- Umożliwić wybór dokładnie jednego modelu bazowego i dokładnie jednego datasetu przetworzonego.
- Odzyskać monitoring istniejącego aktywnego runu bez zgadywania jego `runName`.
- Wysłać chronione żądanie startu treningu i od razu otrzymać `runName`, które zastępuje wcześniejsze pojęcie `training_id`.
- Po akceptacji żądania przejść do monitorowania runu przez kanał `SignalR` po stronie `BE`, bez bezpośredniej komunikacji z `ML`.
- Zablokować możliwość tworzenia kolejki nowych runów: drugi klik Start nie może uruchomić drugiego treningu, ale aktywny run można anulować.

## Adresy / endpointy chronione `FE -> BE`
- `GET /api/trainings/active`
- `GET /api/models/registry`
- `GET /api/datasets/processed`
- `POST /api/trainings`
- `POST /api/trainings/{runName}/cancel`
- `SignalR /ws/trainings/{runName}`

### Anulowanie treningu
- `POST /api/trainings/{runName}/cancel`
- Request body: brak
- `202 Accepted` -> `CancelTrainingRunApiResponse`
- `status` w odpowiedzi opisuje rzeczywisty bieżący stan dopasowanego runu w chwili odpowiedzi, a nie stan "wymuszony" samym kliknięciem Anuluj
- `status` może być `null`, jeśli żądanie `cancel` nie dopasowało żadnego znanego runu i serwer zwrócił uproszczone `202 Accepted` typu no-op
- `requestDisposition` opisuje, czy anulowanie zostało właśnie przyjęte, czy było duplikatem, czy było no-opem dla runu już zakończonego albo niepasującego do żadnego znanego runu

```json
{
  "runName": "train-20260411-130500-cnn-mnist-baseline-sudokuDigitsV1",
  "status": "cancelling",
  "requestDisposition": "cancellationRequested",
  "cancellationRequestedAtUtc": "2026-04-11T13:10:00Z"
}
```

### Kanał postępu
- `SignalR /ws/trainings/{runName}`
- kanał jest logicznie powiązany z jednym `runName`,
- używa tego samego tokenu administracyjnego z `UC-13`,
- klient `SignalR` dostarcza token przez `accessTokenFactory`, a `FE` nie dokleja go ręcznie do URL,
- `FE` nie łączy się bezpośrednio z `ML`; postęp przychodzi wyłącznie z `BE`,
- po połączeniu `BE` najpierw wysyła `snapshot`, a następnie kolejne publiczne eventy stanu,
- `snapshot` jest aktualnym publicznym stanem runu znanym przez `BE` w chwili zestawienia połączenia, a `FE` renderuje go od razu bez oczekiwania na brakujące numery sekwencji,
- jeśli run został zaakceptowany, ale `ML` nie weszło jeszcze w realne wykonywanie, `snapshot` może zwrócić stabilny stan `queued`,
- jeśli run zdążył się już zakończyć przed zestawieniem albo odtworzeniem połączenia, `snapshot` może być terminalny i nieść końcowy stan publiczny znany przez `BE`,
- po dostarczeniu terminalnego `snapshot` kanał może zostać zakończony bez oczekiwania na kolejne eventy,
- każdy event `SignalR` niesie jednocześnie `eventType`, `status`, `stage`, `progress`, `result` i `failure`; `eventType = progress` nie zastępuje `status = running`, tylko opisuje typ komunikatu publicznego,
- dla aktywnego runu eventy `snapshot`, `statusChanged` i `progress` mają `result = null` oraz `failure = null`,
- `FE` nie odsyła aplikacyjnego `ACK` dla eventów `SignalR`; odtworzenie stanu po reconnect odbywa się przez nowy `snapshot`,
- dla końcowego sukcesu event `completed` ma `status = succeeded`, `result != null` i `failure = null`,
- dla końcowego błędu technicznego event `failed` ma `status = failed`, `result = null` i `failure != null`; taki event oznacza, że model wynikowy nie nadaje się do inferencji, a `BE` wykonał już cleanup artefaktów runtime analogiczny do `cancelled`,
- dla anulowania przez użytkownika event `cancelled` ma `status = cancelled`, `result = null` i `failure = null`; publicznie pojawia się dopiero po cleanupie artefaktów runtime i zachowaniu `metadata/{runName}.json`.

## Semantyka właściwości i reguły tworzenia
- `RegistryModelListItemApiResponse.name` jest logiczną nazwą wpisu rejestru modeli i odpowiada katalogowi `models/registry/{name}`.
- `RegistryModelListItemApiResponse.sourceType` przyjmuje wartości `bootstrap` albo `trainingRun`.
- `RegistryModelListItemApiResponse.sourceRunName` może być `null` dla modeli bootstrap.
- `RegistryModelListItemApiResponse.parentModelName` może wskazywać model bazowy użyty do fine-tuningu lub transfer learningu.
- `RegistryModelListItemApiResponse.trainingMode` opisuje istniejący wpis rejestru i sposób jego pochodzenia; nie jest to parametr nowego runu wysyłany przez `FE`.
- `RegistryModelListItemApiResponse.trainingProfileName` i `RegistryModelListItemApiResponse.augmentationProfileName` opisują konfigurację historyczną istniejącego wpisu rejestru; nie są automatycznie dziedziczone przez nowy run.
- `RegistryModelListItemApiResponse.canStartTraining` decyduje, czy dany wpis można wskazać w formularzu startu treningu; `FE` nie powinno próbować odgadywać tego samodzielnie.
- `RegistryModelListItemApiResponse.inputProfile` może zostać pokazane w UI jako metadana zgodności modelu z formatem wejścia.
- W MVP oczekiwana zgodność modelu z datasetem oznacza dokładną równość `inputProfile` i `preprocessingProfile`; ostateczna walidacja należy do `BE`, nie do `FE`.
- `CreateTrainingRunApiEntry.baseModelName` pochodzi bezpośrednio z odpowiedzi `GET /api/models/registry`.
- `CreateTrainingRunApiEntry.processedDatasetName` pochodzi bezpośrednio z odpowiedzi `GET /api/datasets/processed`.
- `TrainingRunApiResponse.runName` jest identyfikatorem runu w API i jednocześnie nazwą plikowego rekordu po stronie serwera.
- `TrainingRunApiResponse.producedModelName` jest logiczną nazwą docelowego wpisu modelu; w MVP może być równe `runName`, ale semantycznie nie jest tym samym.
- Kanoniczna, rozszerzona semantyka `status`, `stage` i `eventType` dla całego `UC-06` jest utrzymywana w `.ai/feature/uc-06-overview.md`; ten dokument opisuje tylko skutki dla publicznego kontraktu `FE`.
- `TrainingRunApiResponse.trainingMode` jest rozwiązywane przez `BE`; w `MVP` ma wartość `fineTuning`, a `FE` nie przekazuje tego pola w requestcie startowym.
- `TrainingRunApiResponse.trainingProfileName` identyfikuje preset parametrów treningu użyty w bieżącym runie.
- `TrainingRunApiResponse.augmentationProfileName` identyfikuje preset augmentacji danych użyty w bieżącym runie.
- W `MVP` `trainingProfileName` i `augmentationProfileName` są rozwiązywane wyłącznie przez `BE` na podstawie własnej polityki i `appsettings.{environment}.json`; `FE` ich nie wysyła i nie edytuje.
- W `MVP` istnieje dokładnie jedna wspierana wartość `trainingProfileName` i dokładnie jedna wspierana wartość `augmentationProfileName`; `FE` nie pobiera osobnego katalogu presetów.
- `TrainingRunApiResponse.benchmarkName` identyfikuje wspólny benchmark wybrany przez `BE` do końcowej ewaluacji.
- `TrainingRunApiResponse.seed` jest ziarnem losowości runu zwróconym informacyjnie przez `BE`.
- `TrainingRunApiResponse.status` używa maszyny stanów `queued`, `starting`, `running`, `cancelling`, `succeeded`, `failed`, `cancelled`.
- `starting` jest stanem przejściowym po stronie `BE` podczas synchronicznego uruchamiania runu; publicznie może pojawić się wyjątkowo tylko w odpowiedzi `GET /api/trainings/active`, jeśli klient trafi w krótkie okno startu obsługiwanego przez `BE`.
- Po udanym `POST /api/trainings` pierwszym stabilnym publicznym statusem zwracanym do `FE` jest `queued`; jeśli start nie zostanie potwierdzony przez `ML`, `BE` robi rollback i zwraca błąd zamiast pozostawiać aktywny run.
- Kanał `SignalR /ws/trainings/{runName}` nie emituje `status = starting`; jeśli `FE` widzi ten stan, pochodzi on z `GET /api/trainings/active`.
- `TrainingRunApiResponse.progressChannelUrl` jest względnym adresem endpointu `SignalR` po stronie publicznego `BE`.
- `CancelTrainingRunApiResponse.status` zwraca bieżący stan dopasowanego runu znany przez `BE` w chwili odpowiedzi albo `null`, jeśli żądanie nie dopasowało żadnego runu.
- `CancelTrainingRunApiResponse.requestDisposition` przyjmuje wartości `cancellationRequested`, `alreadyCancelling`, `noopAlreadyFinished` albo `noopNoMatchingRun`.
- `CancelTrainingRunApiResponse.cancellationRequestedAtUtc` jest timestampem pierwszego skutecznie przyjętego anulowania danego runu i może być `null`, jeśli run zakończył się bez ścieżki anulowania albo żądanie nie dopasowało żadnego runu.
- `TrainingRunSocketEventApiResponse.eventType` używa publicznych wartości `snapshot`, `statusChanged`, `progress`, `completed`, `failed`, `cancelled` i opisuje typ komunikatu, a nie zastępuje pola `status`.
- `TrainingRunSocketEventApiResponse.stage` opisuje grubą fazę techniczną runu; w MVP dopuszczalne wartości to `queued`, `training`, `evaluation`, `finished`.
- `TrainingRunSocketEventApiResponse.sequence` jest rosnącym numerem zdarzenia; `snapshot.sequence` jest równe ostatniej sekwencji zaakceptowanej przez `BE`, a `FE` może ignorować opóźnione eventy o niższym numerze niż ostatnio wyrenderowany stan.
- `FE` nie czeka na brakujące numery `sequence`; renderuje najświeższy stan, który otrzymało.
- Dla aktywnego runu `snapshot`, `statusChanged` i `progress` mają `result = null` i `failure = null`.
- Terminalny `snapshot` może odzwierciedlać końcowy stan publiczny runu: sukces z `result`, błąd z `failure` albo anulowanie bez obu tych pól.
- Event `completed` oznacza sukces runu i ma `status = succeeded`, `result != null`, `failure = null`.
- Event `failed` oznacza błąd techniczny po uruchomieniu runu albo błąd domknięcia workflow, po którym model wynikowy nie nadaje się do inferencji; ma `status = failed`, `result = null`, `failure != null`.
- Event `cancelled` oznacza przerwanie runu na żądanie użytkownika po cleanupie artefaktów runtime; ma `status = cancelled`, `result = null`, `failure = null`.
- `TrainingRunResultApiResponse.reportStatus` opisuje stan raportu końcowego niezależnie od używalności modelu i przyjmuje wartości `ready`, `missing`, `corrupted`.
- Stan `pending` pozostaje wewnętrzny po stronie `BE` w rekordzie runu i nie jest publicznie wysyłany do `FE` przez `SignalR` w trakcie aktywnego runu.
- `TrainingRunResultApiResponse.reportStatus = corrupted | missing` może wystąpić także przy końcowym sukcesie runu; wtedy UI pokazuje ostrzeżenie, ale nie traktuje modelu jako bezużytecznego.
- `TrainingRunFailureApiResponse` nie zawiera `reportStatus`; jeśli jedynym problemem końcowym jest raport, ale model jest używalny, run kończy się `completed`, a nie `failed`.
- `TrainingRunResultApiResponse.primaryArtifactRelativePath` jest ścieżką względną względem `models/registry/{producedModelName}`.
- `TrainingRunResultApiResponse.summaryRelativePath`, `metricsRelativePath` i `confusionMatrixRelativePath` są ścieżkami względnymi względem `trainings/reports/{runName}`.
- `TrainingRunResultApiResponse.*RelativePath` są logicznymi referencjami do artefaktów zapisanych po stronie backendu; `FE` nie buduje z nich ścieżek systemowych.

## Błędy API
- `204 No Content` dla `GET /api/trainings/active`, jeśli nie ma aktywnego runu.
- `400 Bad Request` dla pustego wyboru modelu albo datasetu.
- `401 Unauthorized` dla braku lub wygaśnięcia tokenu administracyjnego.
- `404 Not Found` jeśli model albo dataset zniknęły między odczytem listy a kliknięciem Start.
- `409 Conflict` wyłącznie jeśli inny run jest już aktywny; ten przypadek ma `errorType = training_run_already_active`.
- `422 Unprocessable Content` jeśli wybrany wpis rejestru nie jest poprawnym modelem bazowym do treningu, ma niepoprawny manifest albo `ML` synchronicznie odrzuci start przed akceptacją runu.
- `500 Internal Server Error` jeśli serwer nie może technicznie utworzyć nowego runu mimo wewnętrznych retry rezerwacji nazw i rekordu.
- `503 Service Unavailable` jeśli usługa treningowa albo kanał integracyjny `BE -> ML` są chwilowo niedostępne, a `BE` wycofał prowizoryczny start runu.
- `504 Gateway Timeout` jeśli start treningu nie został potwierdzony w oczekiwanym czasie, a `BE` wycofał prowizoryczny start runu.

```json
{
  "errorType": "training_run_already_active",
  "message": "Inny run treningowy jest już aktywny. System nie tworzy kolejki kolejnych runów."
}
```

## Zasady działania
- Widok `UC-06` jest częścią strefy administracyjnej i wymaga tokenu z `UC-13`.
- Po wejściu na ekran `FE` najpierw wywołuje `GET /api/trainings/active`.
- Jeśli `GET /api/trainings/active` zwróci `200 OK`, interfejs od razu przechodzi do monitoringu istniejącego runu.
- Jeśli `GET /api/trainings/active` zwróci run ze statusem `starting`, UI pokazuje stan typu "Uruchamianie treningu...", blokuje nowy start i krótko odpyta ponownie `GET /api/trainings/active`, aż zobaczy `queued`, `running`, `cancelling` albo `204 No Content` po rollbacku.
- Jeśli `GET /api/trainings/active` zwróci `204 No Content`, `FE` renderuje formularz startu.
- `UC-06` obejmuje nie tylko start runu, ale także odzyskanie monitoringu aktywnego runu, obsługę kanału postępu i anulowanie; `UC-07` rozwija później widok postępu, ale nie redefiniuje transportu ani identyfikatorów.
- `FE` nie buduje samodzielnie listy modeli ani datasetów; zawsze pobiera je z `BE`.
- W formularzu użytkownik wybiera dokładnie jeden wpis modelu bazowego z rejestru i dokładnie jeden dataset `.npz`.
- W `MVP` `FE` nie pokazuje wyboru presetów treningowych ani augmentacyjnych; te wartości są stałe po stronie `BE`.
- `FE` nie zna fizycznego layoutu `model.json` ani `artifacts/`; widzi jedynie logiczne pola zwrócone przez API.
- Model bootstrap bez własnego `runName` może być normalnie pokazany na liście i wybrany do treningu, jeśli `canStartTraining = true`.
- Po sukcesie `POST /api/trainings` interfejs zachowuje `runName`, `producedModelName` i `progressChannelUrl`, aby od razu przejść do monitoringu runu.
- Po sukcesie `POST /api/trainings` interfejs nie oczekuje `status = starting`; odpowiedź startowa zwraca od razu stabilne `queued`.
- Po połączeniu `FE` najpierw renderuje `snapshot`, a potem reaguje na kolejne eventy `statusChanged`, `progress`, `completed`, `failed` i `cancelled`.
- Kanał `SignalR` nie emituje `status = starting`; jeśli UI widzi ten stan, pochodzi on wyłącznie z `GET /api/trainings/active`.
- `snapshot` i późniejsze eventy opisują wyłącznie stan znany przez `BE`; `FE` nie steruje przebiegiem runu przez kanał `SignalR`.
- Jeśli `snapshot` jest terminalny, `FE` renderuje od razu końcowy stan i może przejść do dociągnięcia dodatkowych szczegółów z `GET /api/trainings/{runName}` z `UC-09`.
- W aktywnym runie `FE` opiera UI na `status`, `stage` i `progress`; nie oczekuje publicznego `reportStatus = pending`.
- Po evencie `completed` interfejs czyta dane z `result`.
- Po evencie `failed` interfejs czyta dane z `failure`.
- Po evencie `cancelled` interfejs pokazuje informację o przerwaniu runu bez `result` i bez `failure`.
- Utrata połączenia `SignalR` nie zatrzymuje runu; `FE` powinno próbować reconnectu i po powrocie odtworzyć stan na podstawie `GET /api/trainings/active`, a później z `GET /api/trainings/{runName}` z `UC-09`.
- `FE` nie utrzymuje własnego mechanizmu potwierdzeń `ACK` dla eventów `SignalR` i nie oczekuje replay backlogu; odzyskanie stanu robi przez reconnect i `snapshot`.
- Przycisk Start powinien zostać zablokowany po wysłaniu pierwszego żądania i pozostać nieaktywny, gdy system ma aktywny run.
- Jeśli `POST /api/trainings` zwróci `409 training_run_already_active`, `FE` zawsze traktuje to jako konflikt z istniejącym aktywnym runem; nie próbuje startować drugiego runu, tylko pobiera `GET /api/trainings/active` i przechodzi do monitoringu zwróconego runu.
- `FE` powinno udostępnić akcję anulowania aktywnego runu przez `POST /api/trainings/{runName}/cancel`.
- `POST /api/trainings/{runName}/cancel` jest idempotentne i zawsze zwraca `202 Accepted`; UI traktuje to jako potwierdzenie przyjęcia żądania, a nie jako gwarancję natychmiastowej zmiany statusu.
- Po odpowiedzi `cancel` interfejs czyta `status` jako bieżący stan dopasowanego runu albo `null` przy braku dopasowania oraz `requestDisposition` jako wyjaśnienie, czy anulowanie było nowe, było duplikatem czy było no-opem.
- Jeśli `requestDisposition = noopAlreadyFinished`, UI nie przełącza się sztucznie do stanu `cancelling`, tylko synchronizuje się z otrzymanym stanem końcowym.
- Jeśli `requestDisposition = noopNoMatchingRun`, UI traktuje odpowiedź jako techniczne potwierdzenie no-op i nie zmienia lokalnego stanu na podstawie samego `cancel`.
- Po `401 Unauthorized` `FE` czyści sesję administracyjną i wraca do logowania.
- Po `500 Internal Server Error` formularz powinien zachować wybrane wartości; to błąd techniczny po stronie serwera, a nie sygnał do odzyskiwania aktywnego runu.
- Po `503` albo `504` formularz powinien zachować wybrane wartości, ponieważ `BE` wycofał prowizoryczny start runu i użytkownik może spróbować ponownie bez ponownego wybierania modelu i datasetu.
- Jeśli końcowy event `completed` zawiera `result.reportStatus = corrupted` albo `missing`, UI powinno pokazać ostrzeżenie o uszkodzonym albo brakującym raporcie, ale nie blokować informacji, że model może być nadal używalny.
- Payloady JSON używają kluczy w `camelCase`.
