# UC-11 — Backend

## Cel
- Udostępnić chroniony endpoint listujący kandydatów datasetowych wykrytych automatycznie w skonfigurowanym katalogu `data/raw`.
- Wykonać po stronie `BE` skan skonfigurowanego katalogu `boards` i `digits`, wykryć logicznych kandydatów datasetowych i wykonać podstawową walidację potrzebną do zbudowania listy.
- Zwrócić do `FE` prostą listę logicznych rekordów datasetowych z polami `name` i `type`.

## Adres / endpoint chroniony `FE -> BE`
- `GET /api/datasets/raw-candidates`

## Kontrakt
### `GET /api/datasets/raw-candidates`
- `200 OK` -> `RawDatasetCandidateApiResponse[]`

```json
[
  {
    "name": "v1_training",
    "type": "board"
  },
  {
    "name": "t10k",
    "type": "digit"
  }
]
```

## Błędy API
- `401 Unauthorized` dla braku lub wygaśnięcia tokenu administracyjnego.
- `500 Internal Server Error` dla nieoczekiwanego błędu podczas skanu katalogu lub odczytu plików.

```json
{
  "errorType": "admin_token_expired",
  "message": "Sesja administracyjna wygasła. Zaloguj się ponownie."
}
```

## Modele API wejściowe
- Brak modelu JSON wejściowego.

## Modele API wyjściowe
- `RawDatasetCandidateApiResponse`
  - `name: string`
  - `type: string` (`board` | `digit`)
- `ErrorApiResponse`
  - `errorType: string`
  - `message: string`

## DTO / wyniki use case'ów
- `ListRawDatasetCandidatesQueryResultDto`
  - `items`

## Zasady działania
- `UC-11` obejmuje wyłącznie pobranie listy możliwych datasetów do dalszego przygotowania.
- Wszystkie publiczne endpointy `UC-11` są chronione tokenem z `UC-13`.
- Backend skanuje skonfigurowany katalog wskazany bezpośrednio przez `RawDatasetsStorage.BoardsSubdirectory`.
- Runtime nie zakłada literalnej nazwy folderu `boards`; używa bezpośrednio ścieżki podanej w konfiguracji.
- Pole `type` pozostaje częścią publicznego kontraktu `FE`, mimo że w aktualnym wariancie kandydaci są publikowani wyłącznie jako `board`.
- Typ `digit` wynika z faktu, że kandydat został wykryty w podfolderze `digits`; `BE` nie 
wylicza tego typu przez analizę zawartości pliku.
- Dla `digit` kandydat jest tworzony przez automatyczne sparowanie `*.idx3-ubyte` i `*.
idx1-ubyte` o wspólnym prefiksie wewnątrz folderu `digits`.
- Dla `board` kandydatem jest katalog będący bezpośrednim dzieckiem skonfigurowanego folderu `boards`; publiczne `name` jest nazwą tego katalogu.
- `UC-11` nie wymaga jeszcze rekurencyjnego przeglądania całej zawartości wybranego katalogu `board`; to następuje dopiero w `UC-12` podczas przygotowania datasetu.
- `BE` ignoruje ukryte katalogi techniczne i wpisy nienadające się do wyboru jako dataset źródłowy, np. `.ipynb_checkpoints`.
- Walidacja w `UC-11` pozostaje po stronie `BE` i dotyczy tylko tego, czy dataset może zostać pokazany jako kandydat na liście.
- `BE` nie buduje jeszcze `{name}.npz`, nie zapisuje rekordu przetworzonego datasetu i nie uruchamia workflow przygotowania danych.
- `ML` nie bierze udziału w `UC-11`; przygotowanie i preprocessing należą do `UC-12`.
- Jeśli katalog `data/raw` nie istnieje albo nie zawiera poprawnych kandydatów, endpoint zwraca pustą listę `[]`.
- Publiczne payloady JSON używają kluczy w `camelCase`.

## Założenia implementacyjne
- Publiczny endpoint dopinamy do dedykowanego `DatasetsController`.
- Warstwa `Application` powinna zawierać `ListRawDatasetCandidatesQuery` wraz z walidacją dostępu administracyjnego.
- Skany katalogów i odczyt plików powinny przejść przez porty `Application` i implementacje w `Infrastructure`, bez hardkodowania ścieżek systemowych.
- Konfiguracja katalogów powinna pochodzić z typed options bindowanych w composition root i wskazywać bezpośrednio katalog źródeł `boards` jako `RawDatasetsStorage.BoardsSubdirectory`.
- `appsettings.local.json` i `appsettings.production.json` powinny zawierać dokładną, absolutną ścieżkę do folderu `boards` i `digits`; mimo nazwy `Subdirectory` kod korzysta bezpośrednio z wartości tego pola.
