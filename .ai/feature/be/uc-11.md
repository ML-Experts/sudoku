# UC-11 — Backend

## Cel
- Udostępnić chroniony endpoint listujący kandydatów datasetowych wykrytych automatycznie w skonfigurowanym katalogu `data/raw`.
- Wykonać po stronie `BE` skan katalogu, przejrzeć dwa skonfigurowane podfoldery `boards` i `digits`, wykonać techniczne parowanie plików i podstawową walidację potrzebną do zbudowania listy.
- Zwrócić do `FE` prostą listę logicznych rekordów datasetowych z polami `name` i `type`.

## Adres / endpoint chroniony `FE -> BE`
- `GET /api/datasets/raw-candidates`

## Kontrakt
### `GET /api/datasets/raw-candidates`
- `200 OK` -> `RawDatasetCandidateApiResponse[]`

```json
[
  {
    "name": "Plansze",
    "type": "board"
  },
  {
    "name": "t10k",
    "type": "digit"
  }
]
```

## Błędy API
- `401 Unauthorized` dla braku lub wygaśnięcia tokenu administracyjnego.
- `500 Internal Server Error` dla nieoczekiwanego błędu podczas skanu katalogu lub odczytu plików.

```json
{
  "errorType": "admin_token_expired",
  "message": "Sesja administracyjna wygasła. Zaloguj się ponownie."
}
```

## Modele API wejściowe
- Brak modelu JSON wejściowego.

## Modele API wyjściowe
- `RawDatasetCandidateApiResponse`
  - `name: string`
  - `type: string` (`board` | `digit`)
- `ErrorApiResponse`
  - `errorType: string`
  - `message: string`

## DTO / wyniki use case'ów
- `ListRawDatasetCandidatesQueryResultDto`
  - `items`

## Zasady działania
- `UC-11` obejmuje wyłącznie pobranie listy możliwych datasetów do dalszego przygotowania.
- Wszystkie publiczne endpointy `UC-11` są chronione tokenem z `UC-13`.
- Backend skanuje dwa skonfigurowane katalogi wskazane bezpośrednio przez `RawDatasetsStorage.BoardsSubdirectory` oraz `RawDatasetsStorage.DigitsSubdirectory`.
- Runtime nie zakłada literalnych nazw folderów `boards` i `digits`; używa bezpośrednio ścieżek podanych w konfiguracji.
- Typ `board` wynika z faktu, że kandydat został wykryty w podfolderze `boards`; `BE` nie wylicza tego typu przez analizę zawartości pliku.
- Typ `digit` wynika z faktu, że kandydat został wykryty w podfolderze `digits`; `BE` nie wylicza tego typu przez analizę zawartości pliku.
- Dla `digit` kandydat jest tworzony przez automatyczne sparowanie `*.idx3-ubyte` i `*.idx1-ubyte` o wspólnym prefiksie wewnątrz folderu `digits`.
- Dla `board` kandydat jest tworzony na podstawie wykrytego archiwum `.zip` wewnątrz folderu `boards`.
- Walidacja w `UC-11` pozostaje po stronie `BE` i dotyczy tylko tego, czy dataset może zostać pokazany jako kandydat na liście.
- `BE` nie buduje jeszcze `{name}.npz`, nie zapisuje rekordu przetworzonego datasetu i nie uruchamia workflow przygotowania danych.
- `ML` nie bierze udziału w `UC-11`; przygotowanie i preprocessing należą do `UC-12`.
- Jeśli katalog `data/raw` nie istnieje albo nie zawiera poprawnych kandydatów, endpoint zwraca pustą listę `[]`.
- Publiczne payloady JSON używają kluczy w `camelCase`.

## Założenia implementacyjne
- Publiczny endpoint dopinamy do dedykowanego `DatasetsController`.
- Warstwa `Application` powinna zawierać `ListRawDatasetCandidatesQuery` wraz z walidacją dostępu administracyjnego.
- Skany katalogów i odczyt plików powinny przejść przez porty `Application` i implementacje w `Infrastructure`, bez hardkodowania ścieżek systemowych.
- Konfiguracja katalogów powinna pochodzić z typed options bindowanych w composition root i wskazywać bezpośrednio katalogi źródeł, co najmniej jako `RawDatasetsStorage.BoardsSubdirectory` i `RawDatasetsStorage.DigitsSubdirectory`.
- `appsettings.local.json` i `appsettings.production.json` powinny zawierać dokładne, absolutne ścieżki do folderów `boards` i `digits`; mimo nazwy `Subdirectory` kod korzysta bezpośrednio z wartości tych pól.
