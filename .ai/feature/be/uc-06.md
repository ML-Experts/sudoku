# UC-06 — Backend

## Cel
- Udostępnić chronione API potrzebne do uruchomienia treningu na jednym, wcześniej przygotowanym zestawie `.npz`.
- Pozostać właścicielem workflow, statusów i rekordów systemowych runu po stronie `BE`.
- Traktować `runName` jako jedyny identyfikator procesu treningowego w publicznym API, komunikacji z `ML` i na dysku.
- Egzekwować zasadę pojedynczego aktywnego runu: brak kolejki, brak drugiego równoległego startu, możliwość kooperacyjnego anulowania.
- Finalizować biznesowy wpis modelu wynikowego po zakończeniu runu, bez przenoszenia tej odpowiedzialności do `ML`.

## Zasady utrzymania dokumentu
- Ten plik opisuje wyłącznie kontrakty i odpowiedzialność warstwy `BE` dla `UC-06`.
- Wspólne założenia end-to-end należą do `@.ai/feature/uc-06-overview.md`; tutaj nie duplikujemy całego przepływu `FE` i `ML`.
- Zmiany nanosimy przez aktualizację istniejących sekcji, a nie przez dopisywanie kolejnej rewizji dokumentu na końcu pliku.

## Zakres odpowiedzialności `BE`
- Udostępnia `GET /api/trainings/active`, `GET /api/models/registry`, `GET /api/datasets/processed`, `POST /api/trainings` oraz `POST /api/trainings/{runName}/cancel`.
- Udostępnia kanał `SignalR /ws/trainings/{runName}` do monitorowania aktywnego runu.
- Buduje listę modeli bazowych wyłącznie przez skan `models/registry/*/model.json`.
- Reuse'uje listę gotowych datasetów `.npz` przygotowanych wcześniej w `UC-12`.
- Waliduje możliwość startu runu: autoryzację, istnienie modelu i datasetu, poprawność manifestu, `canStartTraining`, zgodność profili i brak aktywnego runu.
- Generuje `runName` i `producedModelName`, zapisuje rekord `trainings/metadata/{runName}.json` i rozwiązuje wszystkie ścieżki runtime na podstawie `appsettings`.
- Wywołuje `ML`, odbiera eventy `ML -> BE`, aktualizuje własny rekord i dopiero potem publikuje stan do `FE`.
- Finalizuje `models/registry/{producedModelName}/model.json` po zdarzeniu końcowym.
- Nie eksponuje do `FE` ścieżek systemowych ani host-specyficznych lokalizacji plików.

## Poza zakresem `UC-06`
- Historyczny i szczegółowy widok pojedynczego runu przez `GET /api/trainings/{runName}` należy do `UC-09`.
- Dedykowany ekran postępu i komunikaty UI należą do `UC-07`, ale reuse'ują kontrakty zdefiniowane tutaj.
- Wybór aktywnego modelu inferencyjnego należy do `UC-10`.
- Przygotowanie datasetu `.npz` należy do `UC-12`.

### `POST /api/trainings`
- Request body: `CreateTrainingRunApiEntry`
- `202 Accepted` -> `TrainingRunApiResponse`
- W MVP `FE` przekazuje tylko nazwę modelu bazowego i nazwę gotowego datasetu.
- W `MVP` `BE` rozwiązuje konfigurację runu po swojej stronie i przypisuje `trainingMode = fineTuning`; `FE` nie steruje tym polem.
- W `MVP` `BE` rozwiązuje także `trainingProfileName`, `augmentationProfileName`, `benchmarkName` i `seed` na podstawie własnej polityki oraz `TrainingDefaults.*` z `appsettings.{environment}.json`.
- W `MVP` system wspiera dokładnie jeden preset treningowy i dokładnie jeden preset augmentacji po stronie `BE`; `FE` nie pobiera katalogu presetów i nie przekazuje ich identyfikatorów.
- W `MVP` `trainingProfileName` i `augmentationProfileName` nie są dziedziczone z modelu bazowego.
- Jeśli aktywny run już istnieje, endpoint zwraca `409 training_run_already_active` i nie tworzy drugiego wpisu ani kolejki.
- Publiczne `409` jest zarezerwowane wyłącznie dla `training_run_already_active`.
- Jeśli wygenerowany `runName` albo `producedModelName` koliduje z istniejącym stanem plikowym, `BE` retry-uje rezerwację wewnętrznie i nie eksponuje tego jako normalnego `409`.
- Udane `202 Accepted` nigdy nie zwraca `status = starting`; pierwszym stabilnym publicznym statusem odpowiedzi startowej jest `queued`.


### `POST /api/trainings/{runName}/cancel`
- Request body: brak
- `202 Accepted` -> `CancelTrainingRunApiResponse`
- Endpoint służy wyłącznie do kooperacyjnego anulowania aktywnego runu.
- Endpoint jest idempotentny i dla uproszczenia zawsze zwraca `202 Accepted`.
- Jeśli wskazany run jest aktywny albo już `cancelling`, `BE` utrzymuje albo ustawia stan `cancelling` i przekazuje żądanie do `ML`.
- Po potwierdzonym anulowaniu `BE` zachowuje `trainings/metadata/{runName}.json` ze statusem `cancelled`, usuwa artefakty runtime runu i dopiero wtedy publikuje publiczny event `cancelled`.
- Jeśli wskazany run jest już zakończony, nie istnieje albo żądanie nie wywołuje nowej zmiany stanu, `BE` nadal zwraca `202 Accepted` jako potwierdzenie przyjęcia żądania typu no-op.
- `status` w odpowiedzi opisuje rzeczywisty bieżący stan dopasowanego runu w chwili odpowiedzi i może być `null`, jeśli żądanie nie dopasowało żadnego znanego runu.
- `requestDisposition` opisuje, czy anulowanie zostało właśnie przyjęte, było duplikatem czy było no-opem dla runu już zakończonego albo niedopasowanego.

```json
{
  "runName": "train-20260411-130500-cnn-mnist-baseline-sudokuDigitsV1",
  "status": "cancelling",
  "requestDisposition": "cancellationRequested",
  "cancellationRequestedAtUtc": "2026-04-11T13:10:00Z"
}
```

### `SignalR /ws/trainings/{runName}`
- Kanał jest logicznie powiązany z jednym `runName`.
- Używa tego samego tokenu administracyjnego co publiczne endpointy HTTP z `UC-13`.
- Klient `SignalR` dostarcza token przez `accessTokenFactory`, a `FE` nie dokleja go ręcznie do URL.
- Po zestawieniu połączenia `BE` wysyła najpierw zdarzenie `snapshot`.
- `snapshot` jest aktualnym publicznym stanem runu znanym przez `BE` w chwili zestawienia albo odtworzenia połączenia.
- Jeśli run został zaakceptowany, ale `ML` nie weszło jeszcze w realne wykonywanie, `snapshot` może zwrócić stabilny stan `queued`.
- Jeśli run zdążył się już zakończyć przed zestawieniem albo odtworzeniem połączenia, `snapshot` może być terminalny i nieść końcowy stan publiczny znany przez `BE`.
- Po dostarczeniu terminalnego `snapshot` `BE` nie ma obowiązku utrzymywania kanału dłużej niż potrzeba do wysłania tego jednego komunikatu.
- `snapshot.sequence` jest równe ostatniej sekwencji zaakceptowanej przez `BE` dla danego runu.
- Kolejne publiczne eventy to `statusChanged`, `progress`, `completed`, `failed` i `cancelled`.
- Kanał publiczny nie emituje `status = starting`; pierwszym stabilnym publicznym stanem na kanale jest `queued`.
- Każdy publiczny event niesie jednocześnie `eventType`, `status`, `stage`, `progress`, `result` i `failure`; `eventType = progress` nie zastępuje `status = running`, tylko opisuje typ komunikatu.
- Dla aktywnego runu `snapshot`, `statusChanged` i `progress` mają `result = null` oraz `failure = null`.
- `BE -> FE` nie używa dodatkowych potwierdzeń aplikacyjnych `ACK`; po reconnect klient odzyskuje stan przez nowy `snapshot`.
- Event `completed` oznacza sukces runu i ma `status = succeeded`, `result != null`, `failure = null`.
- Event `failed` oznacza błąd techniczny po uruchomieniu runu albo błąd domknięcia workflow, po którym model wynikowy nie nadaje się do inferencji; przed publikacją eventu `BE` wykonuje cleanup artefaktów runtime analogiczny do `cancelled`.
- Event `cancelled` oznacza anulowanie przez użytkownika po cleanupie artefaktów runtime i ma `status = cancelled`, `result = null`, `failure = null`.
- Zerwanie połączenia `SignalR` nie zatrzymuje runu.

### `POST /internal/ml/trainings/{runName}/events`
- Request body: `TrainingRunEventApiEntry`
- `202 Accepted` -> brak body
- Wywołanie jest chronione technicznym mechanizmem service-to-service, a nie tokenem użytkownika z `UC-13`.
- Endpoint jest idempotentny względem pary `runName + sequence`.
- Jeśli `ML` powtórzy event z tym samym `sequence`, `BE` odpowiada `202 Accepted` bez ponownego wykonywania skutków ubocznych, takich jak cleanup czy finalizacja modelu.
- Jeśli `BE` otrzyma event o niższym `sequence` niż `lastAcceptedSequence`, traktuje go jako spóźniony i również odpowiada `202 Accepted` bez cofania stanu.
- Końcowy event `completed`, `failed` albo `cancelled` ma być retry-owany przez `ML` aż do otrzymania odpowiedzi `2xx`; `BE` musi umożliwić takie ponowienia bez psucia workflow.

## Semantyka i reguły
### `runName` i `producedModelName`
- `runName` jest identyfikatorem jednego konkretnego procesu treningowego.
- `runName` spina publiczne API, kanał `SignalR`, rekord `trainings/metadata/{runName}.json`, katalog `trainings/runs/{runName}` i katalog `trainings/reports/{runName}`.
- `producedModelName` jest logiczną nazwą modelu wynikowego tworzonego po zakończeniu runu.
- W MVP `producedModelName` może być równe `runName`, ale semantycznie nie są to te same pola.

### `trainingMode` i konfiguracja runu
- `RegistryModelListItemApiResponse.trainingMode` opisuje istniejący wpis rejestru i jego pochodzenie, a nie parametr nowego startu.
- `TrainingRunApiResponse.trainingMode` oraz `StartTrainingRunApiEntry.resolvedConfiguration.trainingMode` opisują konfigurację bieżącego runu rozwiązaną przez `BE`.
- W `MVP` `BE` przypisuje `trainingMode = fineTuning`, bez udziału `FE`.
- `trainingProfileName` identyfikuje preset parametrów treningu użyty w runie.
- `augmentationProfileName` identyfikuje preset augmentacji danych użyty w runie.
- `benchmarkName` identyfikuje wspólny benchmark używany do końcowej ewaluacji.
- `seed` jest ziarnem losowości runu potrzebnym do powtarzalności eksperymentu.
- W `MVP` `BE` rozwiązuje te pola po swojej stronie na podstawie własnej polityki oraz `TrainingDefaults.*` z `appsettings.{environment}.json`.
- W `local` wartości pochodzą z `appsettings.local.json`, a w `production` z `appsettings.production.json` przygotowanego przez workflow.
- W `MVP` `trainingProfileName` i `augmentationProfileName` nie są dziedziczone z modelu bazowego i nie są podawane przez `FE`.
- W `MVP` istnieje dokładnie jedna wspierana wartość `trainingProfileName` i dokładnie jedna wspierana wartość `augmentationProfileName`; `BE` nie wystawia osobnego katalogu presetów do `FE`.
- `RegistryModelListItemApiResponse.trainingProfileName` i `augmentationProfileName` opisują istniejący wpis rejestru i jego historię, a nie domyślne ustawienia nowego runu.
- W przyszłości to pole może zostać podpięte pod konfigurację albo parametr użytkownika bez zmiany podziału odpowiedzialności między `FE`, `BE` i `ML`.

### Model bootstrap / wpis rejestru
- Model bootstrap ma własny wpis `models/registry/{modelName}` z `model.json` i katalogiem `artifacts/`.
- Taki model może mieć `sourceType = bootstrap`, `sourceRunName = null` i nadal być poprawnym wejściem do `UC-06`.
- Backend nie wymaga historii `trainings/*` dla modelu bootstrap.

### Statusy i `stage`
- Kanoniczna, rozszerzona semantyka `status`, `stage` i `eventType` dla całego `UC-06` jest utrzymywana w `.ai/feature/uc-06-overview.md`; ten dokument opisuje tylko konsekwencje dla kontraktów i workflow `BE`.
- Statusy aktywne: `queued`, `starting`, `running`, `cancelling`.
- Statusy końcowe: `succeeded`, `failed`, `cancelled`.
- `stage` opisuje techniczną fazę runu i nie zastępuje pola `status`.
- W MVP dopuszczalne wartości `stage`: `queued`, `training`, `evaluation`, `finished`.
- `starting` jest stanem przejściowym pomiędzy zapisaniem rekordu runu a synchronicznym potwierdzeniem `202 Accepted` z `ML`.
- Publicznie może pojawić się wyjątkowo tylko przez `GET /api/trainings/active`; nie jest zwracane przez udane `POST /api/trainings` ani emitowane przez `SignalR`.
- Po udanym `POST /api/trainings` pierwszym stabilnym publicznym statusem zwracanym do `FE` jest `queued`.

### Eventy i sekwencja
- Publiczne eventy `BE -> FE`: `snapshot`, `statusChanged`, `progress`, `completed`, `failed`, `cancelled`.
- Wewnętrzne eventy `ML -> BE`: `statusChanged`, `progress`, `completed`, `failed`, `cancelled`.
- `snapshot` jest generowany wyłącznie przez `BE` po zestawieniu kanału i nie pochodzi bezpośrednio z `ML`.
- `snapshot` opisuje aktualny publiczny stan runu znany przez `BE`, a nie surowo ostatni event techniczny otrzymany z `ML`.
- Kanał `SignalR` nie emituje `status = starting`; jeśli `FE` widzi ten stan, pochodzi on co najwyżej z `GET /api/trainings/active`.
- `TrainingRunEventApiEntry.sequence` jest rosnącym numerem zdarzenia w obrębie jednego runu.
- `snapshot.sequence` jest równe ostatniej sekwencji zaakceptowanej przez `BE` w momencie wygenerowania `snapshot`.
- `FE` może ignorować opóźnione eventy o niższym `sequence`, aby nie cofać UI do starszego stanu.
- `FE` nie czeka na brakujące numery sekwencji; renderuje najświeższy stan, który zna.
- `BE` zapisuje ostatnio zaakceptowaną sekwencję i nie cofa stanu przy spóźnionych eventach.
- `BE` traktuje event z tym samym `sequence` jako idempotentne ponowienie i nie wykonuje drugi raz finalizacji, cleanupu ani publikacji.
- Dla aktywnego runu eventy `snapshot`, `statusChanged` i `progress` mają `result = null` i `failure = null`.
- Terminalny `snapshot` może odzwierciedlać końcowy stan publiczny runu: sukces z `result`, błąd z `failure` albo anulowanie bez obu tych pól.
- Event `completed` oznacza sukces runu i ma `status = succeeded`, `result != null`, `failure = null`.
- Event `failed` oznacza błąd techniczny albo błąd domknięcia workflow po uruchomieniu runu i ma `status = failed`, `result = null`, `failure != null`.
- Event `cancelled` oznacza przerwanie runu przez użytkownika po cleanupie artefaktów runtime; ma `status = cancelled`, `result = null`, `failure = null`.
- `failed` oznacza, że model wynikowy nie jest używalny do inferencji; jeśli jedynym problemem końcowym jest raport, ale artefakty modelu są kompletne, run kończy się `completed`, a nie `failed`.

### Zgodność modelu i datasetu
- W MVP zgodność modelu bazowego z datasetem oznacza dokładną równość:
  - `RegistryModel.inputProfile`
  - `ProcessedDataset.preprocessingProfile`
- Walidację tej zgodności wykonuje `BE` przed wywołaniem `ML`.
- `ML` może potraktować brak zgodności jako błąd obronny `422`, ale to `BE` pozostaje pierwszą linią walidacji.

### Pojedynczy aktywny run
- System dopuszcza dokładnie jeden aktywny run jednocześnie.
- `BE` nie buduje kolejki kolejnych runów.
- Drugie kliknięcie Start nie może utworzyć nowego runu.
- Jeśli aktywny run już istnieje, `BE` zwraca `409 training_run_already_active`.
- Publiczne `409` jest zarezerwowane wyłącznie dla konfliktu z istniejącym aktywnym runem.
- Konflikty technicznej rezerwacji `runName` albo `producedModelName` są obsługiwane wewnętrznym retry po stronie `BE` i nie są normalnym publicznym przypadkiem `409`.
- Po takim `409` klient powinien pobrać `GET /api/trainings/active` i przejść do monitoringu istniejącego runu.

### Start synchroniczny i rollback
- `BE` może chwilowo utrzymywać nowo tworzony rekord runu w stanie `starting`, zanim `ML` potwierdzi przyjęcie startu.
- Jeśli wygenerowany `runName` albo `producedModelName` koliduje z istniejącym stanem plikowym, `BE` wykonuje wewnętrzny retry rezerwacji przed wywołaniem `ML`, zamiast zwracać publiczne `409`.
- Jeśli mimo retry nie uda się bezpiecznie zarezerwować nazw albo utworzyć prowizorycznego rekordu runu, `BE` zwraca błąd techniczny `500` i nie uruchamia flow odzyskania aktywnego runu po stronie `FE`.
- Jeśli `ML` nie przyjmie żądania albo wywołanie `BE -> ML` przekroczy timeout, zanim `BE` odpowie do `FE`, `BE` robi rollback prowizorycznego stanu.
- Rollback obejmuje co najmniej usunięcie albo unieważnienie rekordu `trainings/metadata/{runName}.json`, zwolnienie locka aktywnego runu oraz rezerwacji `producedModelName`.
- Jeśli `ML` synchronicznie zwróci błąd walidacyjny albo kontraktowy przed akceptacją runu, `BE` po rollbacku przepuszcza do `FE` ten sam kod HTTP i body; typowym przypadkiem jest `422`.
- Po zwróceniu `202 Accepted` do `FE` run istnieje już systemowo; późniejsze błędy są raportowane jako zdarzenia końcowe, a nie przez rollback startu.

### Anulowanie i utrata połączenia
- `POST /api/trainings/{runName}/cancel` służy do kooperacyjnego anulowania aktywnego runu.
- `BE` przechodzi do stanu `cancelling` i wywołuje `POST /ml/trainings/{runName}/cancel`.
- `ML` sprawdza flagę anulowania między bezpiecznymi etapami pracy i raportuje `cancelled`.
- Po otrzymaniu `cancelled` `BE` zachowuje `trainings/metadata/{runName}.json` ze statusem `cancelled`, usuwa artefakty runtime z `trainings/runs/{runName}`, `trainings/reports/{runName}`, katalogu tymczasowego oraz częściowo utworzonego katalogu `models/registry/{producedModelName}`, a dopiero potem publikuje publiczny event `cancelled`.
- `POST /api/trainings/{runName}/cancel` jest idempotentne i dla uproszczenia zawsze zwraca `202 Accepted`, nawet jeśli żądanie nie wprowadza nowej zmiany stanu.
- `CancelTrainingRunApiResponse.status` zwraca rzeczywisty bieżący stan dopasowanego runu w chwili odpowiedzi albo `null`, jeśli żądanie nie dopasowało żadnego runu.
- `CancelTrainingRunApiResponse.requestDisposition` przyjmuje wartości `cancellationRequested`, `alreadyCancelling`, `noopAlreadyFinished` albo `noopNoMatchingRun`.
- `CancelTrainingRunApiResponse.cancellationRequestedAtUtc` jest timestampem pierwszego skutecznie przyjętego anulowania danego runu i może być `null`, jeśli run zakończył się bez ścieżki anulowania albo żądanie nie dopasowało żadnego runu.
- Zerwanie kanału `SignalR` nie zatrzymuje runu.
- Po reconnect `FE` powinno ponownie połączyć kanał, odebrać `snapshot`, a w razie potrzeby odpytać `GET /api/trainings/active`.

## Przebieg backendowy
1. Użytkownik administracyjny otwiera ekran `UC-06`.
2. `FE` najpierw pyta o aktywny run przez `GET /api/trainings/active`.
3. Jeśli `BE` zwróci `200 OK`, `FE` przechodzi od razu do monitoringu istniejącego runu.
4. Jeśli `BE` zwróci `204 No Content`, `FE` pobiera `GET /api/models/registry` oraz `GET /api/datasets/processed`.
5. Użytkownik wybiera dokładnie jeden model bazowy i dokładnie jeden dataset.
6. `FE` wysyła `POST /api/trainings` z polami `baseModelName` i `processedDatasetName`.
7. `BE` sprawdza token administracyjny, istnienie modelu i datasetu, poprawność manifestu, `canStartTraining`, zgodność profili oraz brak aktywnego runu.
8. Jeśli aktywny run już istnieje, `BE` zwraca `409 training_run_already_active`, a `FE` odzyskuje jego dane przez `GET /api/trainings/active`.
9. Jeśli aktywnego runu nie ma, `BE` generuje `runName` i `producedModelName`; jeśli rezerwacja tych nazw koliduje z istniejącym stanem plikowym, wykonuje wewnętrzny retry zamiast zwracać publiczne `409`.
10. `BE` zapisuje rekord `trainings/metadata/{runName}.json` w przejściowym stanie `starting`, jeszcze przed wywołaniem `ML`.
11. `BE` rozwiązuje wszystkie potrzebne ścieżki absolutne na podstawie `appsettings.{environment}.json`; w `local` pochodzą z `appsettings.local.json`, a w `production` z `appsettings.production.json` przygotowanego przez workflow.
12. `BE` rozwiązuje konfigurację runu; w `MVP` przypisuje `trainingMode = fineTuning` oraz domyślne profile, benchmark i `seed` po swojej stronie, bez dziedziczenia tych wartości z modelu bazowego.
13. `BE` wywołuje `POST /ml/trainings`.
14. Jeśli `ML` nie przyjmie startu albo wywołanie przekroczy timeout, `BE` robi rollback prowizorycznego rekordu; przy synchronicznym błędzie walidacyjnym albo kontraktowym przepuszcza do `FE` ten sam kod i body, a dla niedostępności albo timeoutu zwraca `503` albo `504`.
15. Jeśli `ML` przyjmie run asynchronicznie i odeśle `202 Accepted`, `BE` zwraca do `FE` odpowiedź startową z `runName`, `producedModelName`, `status` i `progressChannelUrl`.
16. `FE` otwiera kanał `SignalR /ws/trainings/{runName}` z tokenem przekazanym przez `accessTokenFactory`.
17. `BE` po połączeniu wysyła `snapshot` aktualnego stanu runu.
18. `ML` wykonuje trening i wysyła eventy do `BE` przez `POST /internal/ml/trainings/{runName}/events`.
19. `BE` aktualizuje własny rekord runu i dopiero wtedy publikuje ten sam stan do `FE`.
20. `ML` zapisuje checkpointy i logi do `trainings/runs/{runName}`, raporty do `trainings/reports/{runName}` oraz finalne artefakty modelu do `models/registry/{producedModelName}/artifacts`.
21. Po zdarzeniu końcowym `completed` `BE` finalizuje `models/registry/{producedModelName}/model.json` i aktualizuje rekord runu o status końcowy, `reportStatus`, ostrzeżenia i referencje do artefaktów.
22. Jeśli końcowy problem dotyczy wyłącznie raportu (`missing` albo `corrupted`), ale artefakty modelu są kompletne, `ML` raportuje `completed`, a `BE` zachowuje model wynikowy i publikuje ostrzeżenie zamiast przechodzić do `failed`.
23. Po zdarzeniu końcowym `failed` `BE` zachowuje `trainings/metadata/{runName}.json` ze statusem `failed`, usuwa artefakty runtime runu z `trainings/runs/{runName}`, `trainings/reports/{runName}`, katalogu tymczasowego oraz częściowo utworzonego katalogu `models/registry/{producedModelName}`, a dopiero potem publikuje publiczny event `failed`.
24. Po zdarzeniu końcowym `cancelled` `BE` zachowuje `trainings/metadata/{runName}.json` ze statusem `cancelled`, usuwa artefakty runtime runu i dopiero potem publikuje publiczny event `cancelled`.

## Rekord runu i pliki
### Co zapisuje `BE`
- `trainings/metadata/{runName}.json`
- finalne `models/registry/{producedModelName}/model.json` wyłącznie po `completed`
- pełną konfigurację eksperymentu, w tym `baseModelName`, `processedDatasetName`, `seed`, `sourceRevision`, profile treningowe oraz referencje do artefaktów potrzebnych później w UI
- W `MVP` pole `sourceRevision` jest zapisywane jawnie jako `null`; pozostaje zarezerwowane do przyszłego śledzenia wersji kodu albo konfiguracji eksperymentu.
- Przy `failed` i `cancelled` `BE` zachowuje rekord `trainings/metadata/{runName}.json`, ale usuwa pozostałe artefakty runtime runu oraz częściowo utworzony katalog modelu wynikowego.

### Co zapisuje `ML`
- `trainings/runs/{runName}`
- `trainings/reports/{runName}`
- `models/registry/{producedModelName}/artifacts` wyłącznie dla runu zakończonego sukcesem
- Jeśli run kończy się `failed`, częściowo utworzone artefakty techniczne mogą istnieć chwilowo, ale cleanup po stronie `BE` usuwa je przed publikacją końcowego eventu.

### `reportStatus` i referencje do artefaktów
- `reportStatus` opisuje stan raportu końcowego niezależnie od statusu runu i przyjmuje w `MVP` wartości `pending`, `ready`, `missing`, `corrupted`.
- W publicznym `TrainingRunResultApiResponse` pole `reportStatus` występuje wyłącznie dla końcowego eventu `completed`, dlatego przyjmuje wartości `ready`, `missing`, `corrupted`.
- Stan `pending` pozostaje wewnętrzny w rekordzie runu po stronie `BE` i nie jest wysyłany do `FE` w trakcie aktywnego runu przez `SignalR`.
- `TrainingRunFailureApiResponse` nie zawiera `reportStatus`; jeśli jedynym problemem końcowym jest raport, ale model jest używalny, run kończy się `completed`, a nie `failed`.
- `primaryArtifactRelativePath` jest ścieżką względną względem `models/registry/{producedModelName}`.
- `summaryRelativePath`, `metricsRelativePath` i `confusionMatrixRelativePath` są ścieżkami względnymi względem `trainings/reports/{runName}`.
- Katalogi bazowe tych referencji wynikają z `appsettings.{environment}.json`.

## Konfiguracja runtime
- `UC-06` wymaga, aby backend miał w `appsettings.local.json` i `appsettings.production.json` dokładne, absolutne ścieżki do katalogów używanych przez workflow treningu.
- Runtime backendu wybiera środowisko zgodnie z mechanizmem opisanym w `src/Backend/Sudoku/Sudoku/Configuration/BackendConfigurationExtensions.cs`.
- `BE` nie hardcoduje ścieżek typu `/opt/sudoku/...`; wszystkie lokalizacje i URL-e integracyjne pochodzą z konfiguracji.
- W `local` ścieżki runtime są wpisane na sztywno w `appsettings.local.json`.
- W `production` ścieżki runtime oraz wartości konfiguracyjne są przygotowywane przez workflow w `appsettings.production.json`.
- Minimalny zestaw ustawień wymaganych po stronie `BE`:
  - `ProcessedDatasetsStorage.DirectoryPath`
  - `ModelsRegistryStorage.DirectoryPath`
  - `TrainingsStorage.RunsDirectoryPath`
  - `TrainingsStorage.ReportsDirectoryPath`
  - `TrainingsStorage.MetadataDirectoryPath`
  - `TrainingsStorage.WorkingDirectoryPath`
  - `BenchmarkStorage.DirectoryPath`
  - `TrainingDefaults.DefaultSeed`
  - `TrainingDefaults.DefaultTrainingProfileName`
  - `TrainingDefaults.DefaultAugmentationProfileName`

## Błędy API
- `400 Bad Request` dla niepoprawnego lub niekompletnego żądania startu.
- `401 Unauthorized` dla braku lub wygaśnięcia tokenu administracyjnego.
- `404 Not Found` jeśli wybrany model bazowy albo dataset `.npz` nie istnieje już w systemie plików.
- `409 Conflict` wyłącznie jeśli istnieje już aktywny run; publiczny `errorType` tego przypadku to `training_run_already_active`.
- `422 Unprocessable Content` jeśli wpis rejestru modeli nie nadaje się do treningu, ma niepoprawny manifest, jest niezgodny z profilem wejścia datasetu albo `ML` synchronicznie odrzuci start przed akceptacją runu.
- `500 Internal Server Error` jeśli `BE` mimo wewnętrznych retry nie może zarezerwować nowego `runName` albo `producedModelName` lub utworzyć prowizorycznego rekordu runu przed akceptacją startu.
- `503 Service Unavailable` jeśli `ML` albo kanał integracyjny `BE -> ML` są chwilowo niedostępne.
- `504 Gateway Timeout` jeśli wywołanie `BE -> ML` podczas startu runu przekroczy limit czasu.
- Dla błędów synchronicznych zwróconych przez `ML` przed akceptacją runu `BE` po rollbacku przepuszcza do `FE` ten sam kod i body.
- Konflikt nazwy wygenerowanej przez serwer nie powoduje publicznego `409`; przypadek jest obsługiwany przez retry, a po wyczerpaniu prób traktowany jako błąd techniczny `500`.
- Dla `503` i `504` `BE` zwraca błąd tylko wtedy, gdy start nie został jeszcze potwierdzony do `FE`; w takim przypadku prowizoryczny rekord runu zostaje wycofany przez rollback.
- `POST /api/trainings/{runName}/cancel` nie używa `409`; dla uproszczenia zawsze zwraca `202 Accepted`.
- Dla `requestDisposition = noopNoMatchingRun` `BE` nie zwraca `404`, aby zachować uproszczony kontrakt anulowania.

```json
  "errorType": "training_run_already_active",
```

## Założenia implementacyjne
- Publiczne endpointy implementujemy przez kontrolery ASP.NET, nie przez minimal API.
- Logika workflow trafia do warstwy `Application`, a kontrolery pozostają cienkie.
- Warstwa `Application` powinna zawierać co najmniej `GetActiveTrainingRunQuery`, `ListRegistryModelsQuery`, `CreateTrainingRunCommand` i `CancelTrainingRunCommand` wraz z walidatorami `FluentValidation`.
- Warstwa `Application` powinna abstrahować od:
  - skanu rejestru modeli,
  - odczytu datasetów przetworzonych,
  - zapisu rekordów plikowych runu,
  - locka pojedynczego aktywnego runu,
  - wywołania `ML`,
  - publikacji eventów `SignalR`.
- Implementacja kanału postępu używa `SignalR`; kontrakt publiczny pozostaje zgodny z `SignalR /ws/trainings/{runName}`, a klient dostarcza token przez `accessTokenFactory` bez ręcznego doklejania go do URL.
- Publiczne i wewnętrzne payloady JSON używają kluczy w `camelCase`.
