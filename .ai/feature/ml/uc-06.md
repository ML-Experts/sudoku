# UC-06 — Machine Learning

## Cel
- Przyjąć od `BE` techniczne żądanie startu treningu na jednym przygotowanym artefakcie `.npz`.
- Uruchomić asynchroniczny run treningowy na podstawie wskazanego modelu bazowego i resolved konfiguracji przekazanej przez `BE`.
- Zapisać artefakty techniczne runu w katalogach runtime przekazanych przez `BE`, przy czym finalny model ma trafić do `models/registry`.
- Raportować do `BE` status, postęp, anulowanie i wynik końcowy tak, aby `ML` nie stał się niezależnym źródłem prawdy dla treningów.
- Wspierać kooperacyjne anulowanie jedynego aktywnego runu oraz dopuścić sytuację, w której raport końcowy jest uszkodzony, ale sam model pozostaje używalny.

## Endpointy wewnętrzne `BE -> ML`
- `POST /ml/trainings`
- `POST /ml/trainings/{runName}/cancel`

## Endpoint wewnętrzny `ML -> BE`
- `POST /internal/ml/trainings/{runName}/events`

## Semantyka właściwości i reguły tworzenia
- `StartTrainingRunApiEntry.runName`:
  - jest generowane przez `BE`,
  - jest wspólnym identyfikatorem runu w katalogach artefaktów i w publicznym API,
  - `ML` nie generuje dla tego procesu własnego równoległego identyfikatora.
- `StartTrainingRunApiEntry.baseModel.directoryPath`:
  - jest absolutną ścieżką do katalogu wpisu modelu w rejestrze,
  - `ML` nie skanuje samodzielnie całego `models/registry` po nazwie.
- `StartTrainingRunApiEntry.baseModel.manifestPath`:
  - jest absolutną ścieżką do `model.json`,
  - `ML` może odczytać z niego techniczne metadane, ale nie traktuje go jako własnego źródła prawdy biznesowej.
- `StartTrainingRunApiEntry.baseModel.primaryArtifactPath`:
  - jest absolutną ścieżką do głównego artefaktu modelu bazowego,
  - `ML` nie wyszukuje tego pliku heurystycznie po nazwie.
- `StartTrainingRunApiEntry.baseModel.inputProfile`:
  - opisuje oczekiwany format wejściowy modelu,
  - musi być zgodny z `processedDataset.preprocessingProfile` albo z uzgodnioną regułą kompatybilności.
- `StartTrainingRunApiEntry.baseModel.sourceType`:
  - `bootstrap` oznacza model seed / imported bez własnego `runName`,
  - `trainingRun` oznacza model pochodzący z wcześniejszego treningu.
- `StartTrainingRunApiEntry.processedDataset.filePath`:
  - jest absolutną ścieżką do gotowego pliku `.npz`,
  - preprocessing i split są już wykonane wcześniej w `UC-12`.
- `StartTrainingRunApiEntry.resolvedConfiguration.trainingProfileName`:
  - wskazuje wersjonowany profil treningowy,
  - `ML` mapuje tę nazwę na konkretny plan treningu, np. liczbę epok, optimizer, scheduler, early stopping.
- `StartTrainingRunApiEntry.outputPaths.runDirectoryPath`:
  - jest katalogiem roboczym runu,
  - może zawierać checkpointy, logi epok i pliki pośrednie.
- `StartTrainingRunApiEntry.outputPaths.reportDirectoryPath`:
  - jest katalogiem raportów końcowych runu,
  - tam trafiają metryki, confusion matrix i pliki podglądowe.
- `StartTrainingRunApiEntry.outputModel.directoryPath`:
  - jest katalogiem docelowym wpisu modelu wynikowego w rejestrze,
  - `ML` zapisuje tam wyłącznie techniczne artefakty modelu, przede wszystkim w `artifacts/`.
- `TrainingRunEventApiEntry.sequence`:
  - jest rosnącym numerem zdarzenia w obrębie jednego runu,
  - `ML` nie powinien emitować późniejszych zdarzeń z niższą sekwencją.
- `TrainingRunEventApiEntry.result.reportStatus`:
  - opisuje stan raportu końcowego niezależnie od używalności modelu,
  - przykładowe wartości: `available`, `corrupted`, `missing`.
- `TrainingRunEventApiEntry.result.canUseProducedModelForInference`:
  - wskazuje, czy finalne artefakty modelu są kompletne,
  - może mieć wartość `true` nawet wtedy, gdy `reportStatus != available`.

## Oczekiwane artefakty plikowe
- `runDirectoryPath` powinien zawierać:
  - checkpointy,
  - logi treningowe,
  - techniczne artefakty pośrednie.
- `reportDirectoryPath` powinien zawierać co najmniej:
  - `summary.json`,
  - confusion matrix lub informację o jej braku,
  - metryki porównawcze benchmarku,
  - ewentualne wykresy treningowe.
- `outputModel.directoryPath` powinien zawierać co najmniej:
  - katalog `artifacts/`,
  - finalny plik modelu albo zestaw artefaktów potrzebnych do inferencji i kolejnego treningu.
- `ML` nie jest właścicielem biznesowego `model.json`; ten manifest finalizuje `BE` po zakończeniu runu na podstawie własnego rekordu i eventów otrzymanych od `ML`.

## Wymagana konfiguracja runtime po stronie `ML`
- `UC-06` wymaga, aby warstwa `ML` również miała środowiskową konfigurację `local` / `production` z dokładnymi, absolutnymi ścieżkami runtime.
- Semantyka pól `ML` musi być zgodna z tym, co `BE` zapisuje w `appsettings.local.json` / `appsettings.production.json`.
- Minimalny zestaw ścieżek wymaganych po stronie `ML`:
  - `ProcessedDatasetsStorage.DirectoryPath`,
  - `ModelsRegistryStorage.DirectoryPath`,
  - `TrainingsStorage.RunsDirectoryPath`,
  - `TrainingsStorage.ReportsDirectoryPath`,
  - `TrainingsStorage.WorkingDirectoryPath`,
  - `BenchmarkStorage.DirectoryPath`.
- Konfiguracja `ML` służy do walidacji katalogów, pracy lokalnej, testów uruchomieniowych i zachowania spójności środowiskowej; mimo to `UC-06` zakłada, że kanoniczne ścieżki konkretnego runu przychodzą od `BE` w kontrakcie `POST /ml/trainings`.
- Poza ścieżkami `ML` powinien mieć skonfigurowane co najmniej:
  - bazowy URL wewnętrzny `BE`,
  - shared secret lub równoważny mechanizm service-to-service dla `POST /internal/ml/trainings/{runName}/events`.

## Błędy API
- `400 Bad Request` jeśli kontrakt startu runu jest niekompletny.
- `404 Not Found` jeśli plik modelu bazowego albo plik `.npz` wskazany przez `BE` nie istnieje.
- `409 Conflict` jeśli `ML` ma już aktywny worker treningowy i dostaje drugi start jako dodatkową warstwę ochrony.
- `422 Unprocessable Content` jeśli model bazowy ma niepoprawny manifest, jest niezgodny z profilem wejścia datasetu albo plik `.npz` ma nieobsługiwany schemat.
- `500 Internal Server Error` dla nieobsłużonego błędu pipeline'u treningowego.

```json
{
  "errorType": "training_run_already_active",
  "message": "Serwis ML wykonuje już aktywny run i nie przyjmuje nowego żądania startu."
```

## Zasady działania
- `ML` nie tworzy własnego publicznego endpointu dla `FE`; cały przepływ jest wywoływany wyłącznie przez `BE`.
- `ML` nie jest `source of truth` dla treningów i modeli; stan systemowy pozostaje po stronie `BE`.
- `ML` nie generuje nowego `training_id`; wspólnym identyfikatorem procesu jest `runName` nadane przez `BE`.
- `ML` zakłada, że dataset `.npz` jest już przygotowany i nie wykonuje ponownie preprocessingu z `UC-12`.
- Model bootstrap/imported bez własnego `runName` jest dla `ML` poprawnym wejściem, jeśli posiada prawidłowy manifest i artefakty wskazane przez `BE`.
- `ML` zapisuje finalny model do `models/registry`, dokładnie w katalogu wskazanym przez `outputModel.directoryPath`, przy czym zapisuje tam wyłącznie techniczne artefakty; `BE` finalizuje `model.json`.
- Benchmark używany do ewaluacji końcowej jest stały i wspólny dla porównań modeli; jego fizyczna lokalizacja pochodzi z `benchmarkDirectoryPath`.
- `ML` może tworzyć checkpointy i pliki robocze, ale nie powinien zapisywać ich w katalogu rejestru modeli zamiast w katalogach treningowych.
- `ML` nie powinien aktualizować `models/active/inference.json`; przełączanie aktywnego modelu należy do `BE` i `UC-10`.
- `ML` powinien zwalidować, że ścieżki wejściowe i wyjściowe przekazane przez `BE` mieszczą się w dozwolonych katalogach runtime dla bieżącego środowiska.
- `ML` powinien wspierać tylko jeden aktywny run jednocześnie jako dodatkową ochronę przed wyścigiem i obejściem logiki `BE`.
- Drugie żądanie startu nie może tworzyć kolejki po stronie `ML`; ma zostać odrzucone.
- Anulowanie jest kooperacyjne: `POST /ml/trainings/{runName}/cancel` ustawia flagę anulowania, a pipeline treningowy powinien sprawdzać ją między bezpiecznymi etapami pracy.
- Zerwanie połączenia `WebSocket` między `FE` i `BE` nie ma żadnego wpływu na run po stronie `ML`.
- Po każdym istotnym przejściu stanu `ML` wysyła event do `BE`, a `BE` dopiero publikuje go do `FE`.
- Jeśli raport końcowy jest uszkodzony, ale finalne artefakty modelu są kompletne, `ML` powinien zakończyć run eventem `completed` z ostrzeżeniem oraz `reportStatus = corrupted`, zamiast automatycznie unieważniać model.
- Payloady JSON używają kluczy w `camelCase`.

  - po przyjęciu żądania powinno mieć wartość `queued`,
  - szczegółowy postęp jest raportowany później w `UC-07`.

## Oczekiwane artefakty plikowe
- `runDirectoryPath` powinien zawierać:
  - checkpointy,
  - logi treningowe,
  - techniczne artefakty pośrednie.
- `reportDirectoryPath` powinien zawierać co najmniej:
  - `summary.json`,
  - confusion matrix,
  - metryki porównawcze benchmarku,
  - ewentualne wykresy treningowe.
- `outputModel.directoryPath` powinien zawierać co najmniej:
  - katalog `artifacts/`,
  - finalny plik modelu albo zestaw artefaktów potrzebnych do inferencji i kolejnego treningu.
- `ML` nie jest właścicielem biznesowego `model.json`; ten manifest finalizuje `BE` po zakończeniu runu na podstawie rekordu treningu i referencji zwróconych przez `ML`.
- Przykładowy docelowy układ katalogu rejestru modelu:

```text
├── model.json
└── artifacts/
    ├── model.keras
    └── finetuned-weights.h5
```

- Przykładowy docelowy układ raportu:

```text

├── summary.json
```

## Wymagana konfiguracja runtime po stronie `ML`

- Semantyka pól `ML` musi być zgodna z tym, co `BE` zapisuje w `appsettings.local.json` / `appsettings.production.json`.

## Błędy API
- `400 Bad Request` jeśli kontrakt startu runu jest niekompletny.
- `404 Not Found` jeśli plik modelu bazowego albo plik `.npz` wskazany przez `BE` nie istnieje.
- `422 Unprocessable Content` jeśli model bazowy ma niepoprawny manifest, jest niezgodny z profilem wejścia datasetu albo plik `.npz` ma nieobsługiwany schemat.
- `500 Internal Server Error` dla nieobsłużonego błędu pipeline'u treningowego.

## Zasady działania
- `ML` nie tworzy własnego publicznego endpointu dla `FE`; cały przepływ jest wywoływany wyłącznie przez `BE`.
- `ML` nie jest `source of truth` dla treningów i modeli; stan systemowy pozostaje po stronie `BE`.
- `ML` nie generuje nowego `training_id`; wspólnym identyfikatorem procesu jest `runName` nadane przez `BE`.
- `ML` zakłada, że dataset `.npz` jest już przygotowany i nie wykonuje ponownie preprocessingu z `UC-12`.
- Model bootstrap/imported bez własnego `runName` jest dla `ML` poprawnym wejściem, jeśli posiada prawidłowy manifest i artefakty wskazane przez `BE`.
- Finalny model po treningu musi zostać zapisany w `models/registry`, dokładnie w katalogu wskazanym przez `outputModel.directoryPath`, przy czym `ML` zapisuje tam artefakty techniczne, a `BE` finalizuje `model.json`.
- Benchmark używany do ewaluacji końcowej jest stały i wspólny dla porównań modeli; jego fizyczna lokalizacja pochodzi z `benchmarkDirectoryPath`.
- `ML` może tworzyć checkpointy i pliki robocze, ale nie powinien zapisywać ich w katalogu rejestru modeli zamiast w katalogach treningowych.
- `ML` nie powinien aktualizować `models/active/inference.json`; przełączanie aktywnego modelu należy do `BE` i `UC-10`.
- `ML` powinien zwalidować, że ścieżki wejściowe i wyjściowe przekazane przez `BE` mieszczą się w dozwolonych katalogach runtime dla bieżącego środowiska.
- Payloady JSON używają kluczy w `camelCase`.
