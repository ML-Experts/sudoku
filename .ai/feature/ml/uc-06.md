# UC-06 — Machine Learning

## Cel
- Przyjąć od `BE` techniczne żądanie startu treningu na jednym przygotowanym artefakcie `.npz`.
- Uruchomić asynchroniczny run treningowy na podstawie wskazanego modelu bazowego i resolved konfiguracji przekazanej przez `BE`.
- Zapisać artefakty techniczne runu w katalogach runtime przekazanych przez `BE`, przy czym finalny model ma trafić do `models/registry`.
- Raportować do `BE` status, postęp, anulowanie i wynik końcowy tak, aby `ML` nie stał się niezależnym źródłem prawdy dla treningów.
- Wspierać kooperacyjne anulowanie jedynego aktywnego runu oraz dopuścić sytuację, w której raport końcowy jest uszkodzony albo brakujący, ale sam model pozostaje używalny.

## Endpointy wewnętrzne `BE -> ML`
- `POST /ml/trainings`
- `POST /ml/trainings/{runName}/cancel`

## Endpoint wewnętrzny `ML -> BE`
- `POST /internal/ml/trainings/{runName}/events`

### `POST /ml/trainings/{runName}/cancel`
- Request body: brak
- `202 Accepted` -> `CancelTrainingRunApiResponse`
- `status` w odpowiedzi opisuje rzeczywisty bieżący stan dopasowanego runu w chwili odpowiedzi
- `status` może być `null`, jeśli żądanie `cancel` nie dopasowało żadnego znanego runu i serwis zwraca uproszczone `202 Accepted` typu no-op
- `requestDisposition` opisuje, czy anulowanie zostało właśnie przyjęte, było duplikatem czy było no-opem dla runu już zakończonego albo niepasującego do żadnego znanego runu

```json
{
  "runName": "train-20260411-130500-cnn-mnist-baseline-sudokuDigitsV1",
  "status": "cancelling",
  "requestDisposition": "cancellationRequested",
  "cancellationRequestedAtUtc": "2026-04-11T13:10:01Z"
}
```

### `POST /internal/ml/trainings/{runName}/events`
- Request body: `TrainingRunEventApiEntry`

## Semantyka właściwości i reguły tworzenia
- `StartTrainingRunApiEntry.runName` jest generowane przez `BE` i jest wspólnym identyfikatorem runu w katalogach artefaktów i w publicznym API.
- `StartTrainingRunApiEntry.baseModel.directoryPath` jest absolutną ścieżką do katalogu wpisu modelu w rejestrze; `ML` nie skanuje samodzielnie całego `models/registry`.
- `StartTrainingRunApiEntry.baseModel.manifestPath` jest absolutną ścieżką do `model.json`; `ML` może odczytać z niego techniczne metadane, ale nie traktuje go jako własnego źródła prawdy biznesowej.
- `StartTrainingRunApiEntry.baseModel.primaryArtifactPath` jest absolutną ścieżką do głównego artefaktu modelu bazowego.
- `StartTrainingRunApiEntry.baseModel.sourceType` przyjmuje wartości `bootstrap` albo `trainingRun`.
- `StartTrainingRunApiEntry.processedDataset.filePath` jest absolutną ścieżką do gotowego pliku `.npz`; preprocessing i split są już wykonane wcześniej w `UC-12`.
- `StartTrainingRunApiEntry.resolvedConfiguration.trainingMode` jest w `MVP` rozwiązywane przez `BE` jako `fineTuning`; `ML` nie wyprowadza tej wartości samodzielnie z modelu wejściowego.
- `StartTrainingRunApiEntry.resolvedConfiguration.trainingProfileName` wskazuje preset parametrów treningu użyty w runie, np. epoki, batch size, learning rate albo politykę zamrażania warstw.
- `StartTrainingRunApiEntry.resolvedConfiguration.augmentationProfileName` wskazuje preset augmentacji danych użyty w runie.
- `StartTrainingRunApiEntry.resolvedConfiguration.benchmarkName` wskazuje benchmark używany do końcowej ewaluacji modelu.
- `StartTrainingRunApiEntry.resolvedConfiguration.seed` jest ziarnem losowości runu potrzebnym do powtarzalności eksperymentu.
- W `MVP` `trainingProfileName` i `augmentationProfileName` są rozwiązywane przez `BE` na podstawie własnej polityki oraz `TrainingDefaults.*` z `appsettings.{environment}.json`; nie są dziedziczone z modelu bazowego.
- W `MVP` istnieje dokładnie jedna wspierana wartość `trainingProfileName` i dokładnie jedna wspierana wartość `augmentationProfileName`; `ML` traktuje je jako stałe wejście przekazywane przez `BE`, a nie jako osobno odkrywany katalog presetów.
- `StartTrainingRunApiEntry.outputPaths.runDirectoryPath` jest katalogiem roboczym runu.
- `StartTrainingRunApiEntry.outputPaths.reportDirectoryPath` jest katalogiem raportów końcowych runu.
- `StartTrainingRunApiEntry.outputModel.directoryPath` jest katalogiem docelowym wpisu modelu wynikowego w rejestrze; `ML` zapisuje tam wyłącznie techniczne artefakty modelu, przede wszystkim w `artifacts/`.
- Kanoniczna, rozszerzona semantyka `status`, `stage` i `eventType` dla całego `UC-06` jest utrzymywana w `.ai/feature/uc-06-overview.md`; ten dokument opisuje tylko zachowanie i kontrakt warstwy `ML`.
- `TrainingRunEventApiEntry.eventType` dopuszcza wartości `statusChanged`, `progress`, `completed`, `failed`, `cancelled`; `ML` nie wysyła eventu `snapshot`.
- `TrainingRunEventApiEntry.sequence` jest rosnącym numerem zdarzenia w obrębie jednego runu.
- `ML` zwiększa `sequence` monotonicznie; `BE` używa tej wartości do odrzucania spóźnionych eventów i idempotentnej obsługi ponowień tego samego eventu, a `FE` nie oczekuje kompletności numeracji.
- `TrainingRunEventApiEntry.stage` opisuje grubą fazę techniczną runu; w MVP dopuszczalne wartości to `queued`, `training`, `evaluation`, `finished`.
- `status = starting` pozostaje przejściowym stanem po stronie `BE` i nie jest emitowany przez `ML`.
- Po zaakceptowaniu startu pierwszym stabilnym statusem raportowanym przez `ML` jest `queued` w odpowiedzi `StartedTrainingRunApiResponse`, a późniejsze eventy opisują już aktywne wykonywanie albo zakończenie runu.
- Dla aktywnego runu eventy `statusChanged` i `progress` mają `result = null` oraz `failure = null`.
- Event `completed` oznacza sukces runu i ma `status = succeeded`, `result != null`, `failure = null`.
- Event `failed` oznacza błąd techniczny albo błąd domknięcia workflow po uruchomieniu runu i ma `status = failed`, `result = null`, `failure != null`.
- Event `cancelled` oznacza bezpieczne zatrzymanie runu na żądanie użytkownika i ma `status = cancelled`, `result = null`, `failure = null`.
- `ML` może powtórzyć wysyłkę eventu z tym samym `sequence`, jeśli nie dostało odpowiedzi `2xx` z `BE`; takie ponowienie nie może zmieniać semantyki payloadu.
- `TrainingRunEventApiEntry.result.reportStatus` opisuje stan raportu końcowego niezależnie od używalności modelu i przyjmuje w `MVP` wartości `ready`, `missing`, `corrupted`.
- Stan `pending` pozostaje wewnętrzny po stronie `BE` w rekordzie runu i nie jest przesyłany przez `ML` w `result`, ponieważ `result` występuje tylko dla końcowego eventu `completed`.
- `TrainingRunEventApiEntry.failure` nie zawiera `reportStatus`; jeśli jedynym problemem końcowym jest raport, ale model jest używalny, `ML` musi wysłać event `completed`, a nie `failed`.
- `TrainingRunEventApiEntry.result.canUseProducedModelForInference` wskazuje, czy finalne artefakty modelu są kompletne.
- `TrainingRunEventApiEntry.result.primaryArtifactRelativePath` musi być ścieżką względną względem `models/registry/{producedModelName}`.
- `TrainingRunEventApiEntry.result.summaryRelativePath`, `metricsRelativePath` i `confusionMatrixRelativePath` muszą być ścieżkami względnymi względem `trainings/reports/{runName}`.
- `TrainingRunEventApiEntry.result.*RelativePath` muszą być ścieżkami względnymi względem katalogów kontrolowanych przez `BE`, bez host-specyficznych ścieżek absolutnych.
- W MVP zgodność modelu bazowego z datasetem oznacza dokładną równość `baseModel.inputProfile` i `processedDataset.preprocessingProfile`.
- `ML` traktuje brak tej zgodności jako błąd obronny `422`, nawet jeśli `BE` powinno wychwycić to wcześniej.

## Oczekiwane artefakty plikowe
- `runDirectoryPath` powinien zawierać checkpointy, logi treningowe i techniczne artefakty pośrednie.
- `reportDirectoryPath` powinien zawierać co najmniej `summary.json`, confusion matrix lub informację o jej braku, metryki porównawcze benchmarku i ewentualne wykresy treningowe.
- `outputModel.directoryPath` powinien zawierać co najmniej katalog `artifacts/` oraz finalny plik modelu albo zestaw artefaktów potrzebnych do inferencji i kolejnego treningu wyłącznie dla runu zakończonego sukcesem.
- `ML` nie jest właścicielem biznesowego `model.json`; ten manifest finalizuje `BE` wyłącznie po końcowym evencie `completed`.
- Dla `failed` i `cancelled` mogą istnieć częściowe artefakty techniczne, ale po zachowaniu `trainings/metadata/{runName}.json` cleanup tych artefaktów koordynuje `BE`.
- `ML` może zapisać w raportach własne techniczne metadane wersji środowiska, ale kanoniczny rekord wersji runu dla workflow pozostaje po stronie `BE`.

## Wymagana konfiguracja runtime po stronie `ML`
- `ProcessedDatasetsStorage.DirectoryPath`
- `ModelsRegistryStorage.DirectoryPath`
- `TrainingsStorage.RunsDirectoryPath`
- `TrainingsStorage.ReportsDirectoryPath`
- `TrainingsStorage.WorkingDirectoryPath`
- `BenchmarkStorage.DirectoryPath`
- bazowy URL wewnętrzny `BE`
- shared secret lub równoważny mechanizm service-to-service dla `POST /internal/ml/trainings/{runName}/events`
- Kanonicznym źródłem ścieżek wejścia i wyjścia pozostaje resolved konfiguracja przekazana przez `BE`, wyliczona z `appsettings.{environment}.json`; w `local` pochodzi z `appsettings.local.json`, a w `production` z `appsettings.production.json` przygotowanego przez workflow.

## Błędy API
- `400 Bad Request` jeśli kontrakt startu runu jest niekompletny.
- `404 Not Found` jeśli plik modelu bazowego albo plik `.npz` wskazany przez `BE` nie istnieje.
- `409 Conflict` jeśli `ML` ma już aktywny worker treningowy i dostaje drugi start jako dodatkową warstwę ochrony.
- `422 Unprocessable Content` jeśli model bazowy ma niepoprawny manifest, jest niezgodny z profilem wejścia datasetu albo plik `.npz` ma nieobsługiwany schemat.
- `500 Internal Server Error` dla nieobsłużonego błędu pipeline'u treningowego.

```json
{
  "errorType": "training_run_already_active",
  "message": "Serwis ML wykonuje już aktywny run i nie przyjmuje nowego żądania startu."
}
```

## Zasady działania
- `ML` nie tworzy własnego publicznego endpointu dla `FE`; cały przepływ jest wywoływany wyłącznie przez `BE`.
- `ML` nie jest `source of truth` dla treningów i modeli; stan systemowy pozostaje po stronie `BE`.
- `ML` nie generuje nowego `training_id`; wspólnym identyfikatorem procesu jest `runName` nadane przez `BE`.
- `ML` zakłada, że dataset `.npz` jest już przygotowany i nie wykonuje ponownie preprocessingu z `UC-12`.
- Model bootstrap bez własnego `runName` jest dla `ML` poprawnym wejściem, jeśli posiada prawidłowy manifest i artefakty wskazane przez `BE`.
- `ML` zapisuje finalny model do `models/registry`, dokładnie w katalogu wskazanym przez `outputModel.directoryPath`, przy czym zapisuje tam wyłącznie techniczne artefakty i robi to tylko dla runu zakończonego sukcesem; `BE` finalizuje `model.json`.
- Benchmark używany do ewaluacji końcowej jest stały i wspólny dla porównań modeli; jego fizyczna lokalizacja pochodzi z `benchmarkDirectoryPath`.
- `ML` może tworzyć checkpointy i pliki robocze, ale nie powinien zapisywać ich w katalogu rejestru modeli zamiast w katalogach treningowych.
- `ML` nie powinien aktualizować `models/active/inference.json`; przełączanie aktywnego modelu należy do `BE` i `UC-10`.
- `ML` powinien zwalidować, że ścieżki wejściowe i wyjściowe przekazane przez `BE` mieszczą się w dozwolonych katalogach runtime dla bieżącego środowiska.
- `ML` powinien wspierać tylko jeden aktywny run jednocześnie jako dodatkową ochronę przed wyścigiem i obejściem logiki `BE`.
- Drugie żądanie startu nie może tworzyć kolejki po stronie `ML`; ma zostać odrzucone.
- Jeśli `ML` odrzuci żądanie startu albo nie potwierdzi go w oczekiwanym czasie, `BE` może wycofać swój prowizoryczny rekord runu; `ML` nie powinien w takim przypadku uruchamiać częściowego joba w tle.
- Anulowanie jest kooperacyjne: `POST /ml/trainings/{runName}/cancel` ustawia flagę anulowania, a pipeline treningowy powinien sprawdzać ją między bezpiecznymi etapami pracy.
- Jeśli anulowanie zostało już wcześniej przyjęte albo żądanie nie wprowadza nowej zmiany stanu, `POST /ml/trainings/{runName}/cancel` może idempotentnie zwrócić ponownie `202`; dla runu niepasującego do żadnego znanego wpisu również zwraca `202` typu no-op.
- `CancelTrainingRunApiResponse.status` zwraca rzeczywisty bieżący stan runu znany przez `ML` w chwili odpowiedzi albo `null`, jeśli nie znaleziono dopasowania.
- `CancelTrainingRunApiResponse.requestDisposition` przyjmuje wartości `cancellationRequested`, `alreadyCancelling`, `noopAlreadyFinished` albo `noopNoMatchingRun`.
- `CancelTrainingRunApiResponse.cancellationRequestedAtUtc` jest timestampem pierwszego skutecznie przyjętego anulowania danego runu i może być `null`, jeśli run zakończył się bez ścieżki anulowania albo nie znaleziono dopasowania.
- `ML` wysyła event `cancelled` dopiero po bezpiecznym zatrzymaniu pipeline'u i zwolnieniu własnych zasobów wykonawczych; publiczny event `BE -> FE` pojawia się później, po cleanupie artefaktów runtime po stronie `BE`.
- Zerwanie połączenia `SignalR` między `FE` i `BE` nie ma żadnego wpływu na run po stronie `ML`.
- Po każdym istotnym przejściu stanu `ML` wysyła event do `BE`, a `BE` dopiero publikuje go do `FE`.
- Dla aktywnego runu eventy `statusChanged` i `progress` mogą być traktowane jako best-effort, ale końcowy event musi być dowieziony do `BE` niezawodnie.
- Retry końcowego eventu powinno używać backoffu i nie może trzymać zajętych zasobów GPU/CPU tylko po to, aby potwierdzić zapis stanu w `BE`.
- Jeśli raport końcowy jest uszkodzony albo brakujący, ale finalne artefakty modelu są kompletne, `ML` powinien zakończyć run eventem `completed` z ostrzeżeniem oraz `reportStatus = corrupted` albo `missing`, zamiast automatycznie unieważniać model.
- Payloady JSON używają kluczy w `camelCase`.
